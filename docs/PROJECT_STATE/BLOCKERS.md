# ControlPlane.ai — Blockers & Unresolved Architecture Questions

Per the implementation bootstrap: these are reported, not silently fixed. Each needs an explicit decision before the layer it affects can be implemented cleanly. "Blocks Layer N" means Layer N can technically start without it, but will accumulate rework if the question isn't settled first.

## B1 — No root `AGENTS.md`; two docs reference a file that doesn't exist
`docs/architecture/RUNTIME_FLOW.md` (line ~2481) and `docs/specs/CONTROLPLANE_RAG_RETRIEVAL_HALLUCINATION_AGENT_GUIDE.md` (line 9) list `AGENTS.md` as required reading. No such file exists anywhere in the repo — only `docs/architecture/AGENTS_RESEARCH_ALIGNED_UPDATED.md`, which is itself written as agent operating instructions ("You are an implementation agent...").
**Options:** (a) copy/symlink `AGENTS_RESEARCH_ALIGNED_UPDATED.md` to a root `AGENTS.md`, (b) rename it and update the ~2 references, (c) create a short root `AGENTS.md` that points to the real file.
**Recommendation:** (a) or (c) — cheapest, no content loss. **Blocks:** nothing structurally, but every future coding-agent session that looks for `AGENTS.md` at the root (as this bootstrap itself instructed) will silently miss it without a redirect.

## B2 — No single `docs/ARCHITECTURE.md`; multiple docs reference one
Several docs (`ControlPlane_High_Level_Architecture_OPTIMAL.md` §35, `CONTROLPLANE_CROSS_CUTTING_SYSTEM_SPEC.md`, this bootstrap) reference `docs/ARCHITECTURE.md` or a "Master Specification" as if it were one file. The actual structure is a `docs/architecture/` **directory** of 10 files. `CONTROLPLANE_FINAL_ARCHITECTURE_IMPLEMENTATION_MASTER_SPEC.md` is the closest candidate (it explicitly lists a source-of-truth order over the other 9), but no doc anywhere calls it "docs/ARCHITECTURE.md" or "the Master Specification" by name — it only says "Master implementation-planning specification."
**Recommendation:** confirm `CONTROLPLANE_FINAL_ARCHITECTURE_IMPLEMENTATION_MASTER_SPEC.md` is "the" master doc and either rename it or add a redirect stub at the referenced path. **Blocks:** nothing immediately; matters once tooling starts resolving these paths programmatically.

## B3 — Terminology proliferation across `docs/architecture/` and `docs/specs/` is only partially resolved
The 2026-08-27 audit found dozens of independently-drafted, non-identical vocabularies for the same concepts (event names, budget-field naming, confidence taxonomies, model-router action vocabularies, "impact" enums, capability lists) across the ~24,000 lines in `docs/architecture/` and `docs/specs/`. Only the five highest-impact ones were reconciled (`CONTROLPLANE_FINAL_ARCHITECTURE_IMPLEMENTATION_MASTER_SPEC.md` §64). Examples still open: `SWITCH_MODEL` (routing) vs. `CHANGE_MODEL` (intervention) as possibly-the-same action; three different "remaining budget" field-naming conventions in `INTERVENTION_ENGINE_IMPLEMENTATION_SPEC.md`; four non-identical event-name lists across `PRODUCT_THESIS_UPDATED.md` alone; `ENTERPRISE_DATA` used as a capability in one example without being in the capability enum.
**Recommendation:** resolve opportunistically as each layer touches the relevant contract, rather than as one large rewrite — most of these require an engineering judgment call (are two vocabularies the same mechanism, or genuinely different sub-systems?) that a docs-only pass shouldn't make silently.
**Blocks:** writing type-safe interfaces/enums for Layers 3 (Event Model), 14 (Decision Engine), 15 (Intervention Engine), and 16 (Replanning) — pick one canonical value set per interface as you build it and record the choice in this file.

## B4 — Two incompatible "synthetic enterprise" datasets, never reconciled
`data/synthetic_enterprise/database/*.csv` (8 files, SaaS-company shape: customers with ARR/tier/NPS, products, orders, transactions with payment gateway) and `init_postgres_schema.sql`'s `enterprise_demo` schema (NexaConsult Global, consulting-firm shape: clients, projects, timesheets, invoices, OKRs) describe different companies with no overlapping table names except `departments`, `employees`, `support_tickets`, `conversations`. Both are "COMPLETE" per `DATASET_REGISTRY.md`.
**Recommendation:** decide which one Layer 6 (Synthetic Data Environment) actually loads into Postgres for the working prototype. The NexaConsult schema is more developed (16 tables, referenced by the NexaConsult evaluation query set) and is what `init_postgres_schema.sql` already creates — likely the better default — but the CSVs would need a real decision to either be loaded as-is into a second schema or discarded.
**Progress (2026-08-28, Milestone 4):** resolved for the one concrete consumer that needed a decision — `controlplane/capabilities/sql_capability.py` uses NexaConsult (via a local SQLite build from the real, data-complete `nexaconsult_enterprise.sql` seed script, since the Postgres version of that schema ships zero seed rows). The CSV dataset remains unloaded and undecided for any *other* future consumer.
**Blocks:** nothing for the SQL capability now; still open for Layer 6 proper (loading either/both into ControlPlane's own Postgres) and the CSV dataset's fate.

## B5 — No real model responses or human annotations exist
All 270 `annotation_cases.json` records carry `provenance: SYNTHETIC` and placeholder `model_response` text (literally `"[Synthetic Response Content Generated by Evaluation Simulator]"`). No LLM has actually been called against the query-profile dataset, and no human has actually labeled a case. Every evaluation-layer design in the specs assumes this data exists in some real form.
**Recommendation:** not a blocker for Layers 1–12 (which don't need real evaluation data), but is a hard blocker for Layer 13 (Baseline Evaluation) producing meaningful results, and for any claim of "the system was evaluated."
**Blocks:** Layer 13+, and specifically the "BASELINE vs. CONTROLPLANE" comparison experiment described throughout the docs.

## B6 — `SOURCES_AND_CAPABILITIES.md`'s canonical enums don't match the generated data (PARTIALLY ADDRESSED, Milestone 2)
`docs/DATA/SOURCES_AND_CAPABILITIES.md` defines 6 `required_data_sources` values and 7 `required_capabilities` values. The actual 270-record query-profile dataset uses ~28 and ~24 much more granular, different values respectively (e.g. `enterprise_hr_system`, `analytical_reasoning`) with essentially no overlap in spelling.
**Progress (2026-08-28, Milestone 2):** `controlplane/query_intelligence/knn_profiler.py`'s `_SOURCE_TO_CANONICAL` mapping now translates a subset of the granular values onto the canonical 6-value enum, and the Query Profiler is the first code to actually emit canonical values in `QueryFingerprint.data_requirement`. This is a partial, best-effort mapping (only unambiguous matches are mapped; the rest are dropped rather than guessed) — it does not resolve the underlying question of which vocabulary should be authoritative for the *generated dataset itself* (`data/raw/generated/query_profiles_large.json` still carries the granular, unreconciled values).
**Progress (2026-08-28, Milestone 3):** Layer 9 (Data/Capability Routing) is now implemented — `controlplane/routing/capability_router.py` consumes `QueryFingerprint.capability_hints`/`data_requirement` for real, building an `ExecutionGraph` and applying policy restriction. It still consumes the canonical values only (via the Query Profiler), not the raw dataset's granular values, so the underlying reconciliation question below remains open.
**Recommendation:** still open — decide whether the generated dataset should eventually be remapped/regenerated against the canonical vocabulary, or whether the canonical doc should be extended to a two-level taxonomy (canonical category -> granular value).
**Blocks:** nothing further for routing (Layer 9 is done); still blocks any future use of the raw dataset's granular `required_data_sources`/`required_capabilities` values directly (e.g. a future fine-tuned classifier trained on that dataset).

## B7 — Original competition brief is not fully captured as text
`Problem_Statement/` contains 5 JPEG screenshots of a PDF that its own page indicator marks as `1/7` — i.e. only a subset of a 7-page document, and not transcribed anywhere as markdown. The captured pages establish: this is the Accenture Innovation Challenge 2026, Round 2, Problem Track 1; deliverables are a business proposal + working prototype + pitch; the reference scale parameter is "tens of thousands of interactions per week" (stated as directional, "not a fixed dataset") — which the docs operationalize as a precise "10,000/week" figure; and a detailed "Solutioning Areas" list (detection techniques, decision logic/tiered responses, architecture placement, governance, feedback loops, metrics/dashboard) that is only loosely reflected in `PRODUCT_THESIS_UPDATED.md`.
**Recommendation:** obtain the remaining pages and transcribe the full brief into `Problem_Statement/BRIEF.md` so it stops being an un-searchable image-only artifact and future contributors don't have to re-derive it.
**Blocks:** nothing technically, but risks the team building against a paraphrase of the requirements rather than the requirements themselves.

## B9 — Embedding k-NN baseline (`HybridQueryProfiler`) does not reproduce exactly across sessions/environments (found 2026-08-28, Milestone 3) — **FIXED 2026-08-28, Milestone 5**

**Fix:** `controlplane/models/embedding_cache.py` (`cached_embed_batch`) computes embeddings once, caches them to a committed `.npz` file keyed by (model revision, exact input texts) -- deliberately *excluding* the installed library version from the cache key, so a `pip install --upgrade` can never silently change results for already-cached inputs. Applied to both the Query Profiler's exemplar bank (`data/cache/exemplar_embeddings.npz`) and the new RAG ingestion pipeline (`data/cache/rag_chunk_embeddings.npz`). Verified: deleting and rebuilding the cache, then re-running `evaluate_query_profiler.py`/`evaluate_risk_profiler.py` twice in separate process invocations, produces bit-for-bit identical numbers both times. Dependency versions (`torch==2.13.0`, `sentence-transformers==6.0.0`, `huggingface_hub==1.29.0`, `numpy==2.4.6`) also pinned in `pyproject.toml` as a secondary measure. **Not independently re-verified against an actual different library version** (would require downgrading/upgrading the working environment, risking destabilizing it for a diagnosis that doesn't change the fix) — the cache mechanism structurally guarantees reproducibility regardless, which is what actually mattered for this blocker.

**Original finding, retained for the historical record:**

Re-running `controlplane/experiments/evaluate_query_profiler.py` and `evaluate_risk_profiler.py` in this session, with **zero code changes** to `controlplane/query_intelligence/`, `controlplane/models/local_hf_provider.py`, or any dataset file (confirmed via `git diff --stat` against the Milestone 2 commit), produced different numbers than the ones recorded in that commit for every metric that depends on `EmbeddingKNNQueryProfiler` (complexity accuracy 0.357→0.500, ambiguity 0.857→0.750, risk severity accuracy 0.607→0.500 before the Milestone 3 risk fix was even applied). `RuleBasedQueryProfiler`-only metrics reproduced exactly, bit-for-bit. Confirmed stable (not flaky) across repeated runs within this session, including with `OMP_NUM_THREADS=1`/`MKL_NUM_THREADS=1` forced — ruling out simple BLAS-thread nondeterminism as the mechanism.
**Leading hypothesis:** a `torch`/`sentence-transformers` version difference between the Milestone 2 session's environment and this one (e.g. picked up by a `pip install` between sessions), changing low-level numeric kernels enough to flip a few near-tied cosine-similarity majority votes for borderline validation examples. Not confirmed by directly diffing installed package versions across sessions (no record of the exact Milestone 2 environment's package versions was kept).
**Recommendation:** pin exact `torch`/`sentence-transformers`/`huggingface_hub` versions in `pyproject.toml` (currently unpinned or loosely pinned), and/or cache the exemplar bank's precomputed embeddings to disk (`controlplane/query_intelligence/exemplar_bank.py`) so a given code+data version always encodes to the same vectors regardless of which library version computed them originally.
**Blocks:** nothing structurally, but means any single evaluation run's exact percentage should be treated as approximate (±a few points on k-NN-dependent fields) until this is fixed — already reflected in how `docs/EVALUATION/QUERY_PROFILER_RESULTS.md`/`RISK_PROFILER_RESULTS.md` report numbers (same-session A/B comparisons, not cross-session point comparisons, for anything measuring a code change's effect).

## B10 — Low disk space causing severe, environment-wide slowdowns (found 2026-08-28, Milestone 7)

While re-running the full test suite after Milestone 7's changes, wall-clock time ballooned from the normal ~20-90s to 76+ minutes, and even unrelated commands (`docker ps`, a PowerShell system-resource query) became extremely slow or timed out. Investigated rather than assumed to be a code regression: `pytest --durations=0` on a 7-test file showed all individual test/setup/teardown durations summing to ~2.8s, against a reported total of 166s for that same run — the slowness is not in the test logic at all. `Get-PSDrive C` showed only ~4.5GB free on the system drive. Most likely cause: this milestone's Local Judge download (`Qwen2.5-1.5B-Instruct`, ~3GB) pushed free space critically low, and Windows performs poorly (disk fragmentation pressure, pagefile contention) below roughly 5-10GB free.
**Not fixed:** freeing disk space is a user/environment decision (deleting arbitrary files without instruction would be inappropriate); no code change is warranted since the underlying logic is confirmed fast and correct.
**Recommendation:** free disk space (e.g., clear unused Docker images/volumes, temp files) if test suite wall-clock time matters for future sessions.
**Blocks:** nothing structurally — all 252 tests still pass; this only affects wall-clock time, not correctness.

## B8 — No `docs/ALGORITHMS/` directory

**Blocks:** Layer 7 (Baseline Query Intelligence) onward, per the project's own rule — create the first `docs/ALGORITHMS/QUERY_PROFILER.md` before or alongside that layer's code.
